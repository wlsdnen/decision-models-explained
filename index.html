Jev 원리: 답을 쓰지 않고 읽는 결정 모델

TypeSafe AI의 Jev와 다른 결정 모델들이 어떻게 동작하고 학습되는지 설명한다. 2026-10-09 기준.

1. 답을 쓰지 않고 읽는다

생성 모델은 답을 토큰 하나씩 써 내려간다. 결정 모델은 아무것도 쓰지 않고, 답이 들어갈 빈칸의 점수표에서 후보만 읽어 확률로 바꾼다.

어떻게 읽나

  1. 점수표. 모델은 빈칸마다 다음에 올 수 있는 모든 토큰에 점수를 매긴다. 이 점수가 logit이다.
  2. 후보만 남기기. 질문이 답으로 인정하는 토큰, 곧 허용 토큰만 남긴다. 예/아니오 질문이면 yes와 no다. Jev는 이런 질문 타입을 Noul이라 부른다. 후보가 여러 토큰으로 된 단어면 첫 토큰을 읽고, 첫 토큰이 겹치면 다음 빈칸을 한 번 더 읽어 확률을 곱한다14. Hopper는 보기에 A, B, C 글자를 붙여 그 글자의 logit만 읽는다15 자체 보고.
  3. 확률로 바꾸기. 남은 점수에 softmax(점수 목록을 합이 1인 확률로 바꾸는 함수)를 적용한다. 버린 칸은 빠지므로 후보끼리 다시 나눈 확률이 된다(그림 1-2). 그 전에 logit을 온도로 나눠 조정하기도 한다(4절).
깊이 보기: logit 읽기 의사코드

stephanj의 PCD README "The technique" 단계 3-4와 Hopper 모델 카드의 읽기 방식을 한 질문에 맞춰 옮겼다. 첫 토큰이 같은 선택지는 단계별로 forward pass를 더 하고, 그 선택지의 확률은 단계별 확률의 곱이다14.

prompt  = render(state, question, allowed) + '"answer": "'  # suffix ends where the answer would start
logits  = model.forward(prompt)[-1]          # one forward pass, logits at the last position
ids     = [first_token(v) for v in allowed]  # allowed tokens, e.g. "yes", "no"
z       = logits[ids]                        # discard the rest of the vocabulary
p       = softmax(z / T[question.type])      # Hopper: per-type temperature map
answer  = allowed[argmax(p)]
return answer, p                             # nothing is generated: 0 output tokens

Hopper 카드는 이를 a softmax over the logits of the option letters (A, B, C, ...), restricted to as many letters as there are options라고 쓴다15. 온도 T는 4절에서 다룬다.

왜 빠른가

글을 쓰지 않기 때문이다. 일반 LLM은 답의 토큰 수만큼 계산(forward pass)을 되풀이하고, 결정 모델은 답 빈칸 하나만 계산한다(그림 1-3). 다만 "yes 또는 no 한 단어로 답하라"고 한 LLM도 토큰 하나만 생성하면 끝나므로, 그런 LLM보다 빠르다고 할 수는 없다8. 질문을 묶을 때 메일을 한 번만 읽는 효과는 2절에서 다룬다.

깊이 보기: forward pass 횟수와 비용

생성의 2회차부터는 KV cache 재사용(앞서 계산한 중간 결과를 다시 쓰는 것)으로 새 토큰 하나만 처리한다. 그래서 forward pass 횟수의 차이가 곧 비용의 차이는 아니다. 보기마다 따로 점수를 내는 계열은 보기 수만큼, PCD는 스키마 전체에 2회를 쓴다(3절 비교표). TypeSafe는 Jev가 토큰별로 생성하지 않고 모든 확률을 병렬로 낸다고만 쓴다1 업체 발표.

stephanj의 구현은 세 단계로 일한다14. 먼저 스키마와 상태를 한 번 forward pass를 해 KV cache를 만든다. 다음으로 질문마다 시퀀스를 하나씩 두고, 모든 시퀀스가 그 KV cache를 공유한다. 구현에서는 질문을 "필드"라고 부른다. 각 시퀀스는 "field": "로 끝나므로 다음 자리가 답 자리다. 마지막으로 한 배치 forward pass로 각 시퀀스의 허용 토큰 logit을 읽는다. 저자는 이렇게 하면 토큰별 생성 없이 forward pass 두 번으로 끝난다고 쓴다.

시퀀스가 질문마다 따로이므로 한 질문은 다른 질문의 글을 보지 않는다. MoJev는 attention 마스크로 같은 격리를 만든다. attention 마스크는 각 토큰이 어느 토큰을 참고할지 정하는 표다. MoJev README는 각 후보가 상태, 자기 질문, 자기 토큰만 참고한다고 쓴다19 자체 보고. 모든 결정 모델이 상태를 공유하지는 않는다. Decision 1.0은 질문마다 forward pass를 한 번씩 하고 상태 활성값을 재사용하지 않는다8.

커뮤니티 트래커는 Decoding, Trained, Diffusion 등으로 나눈다.25 이 문서의 A는 Decoding, B부터 E는 Trained, F는 Diffusion에 해당한다.

보통은 어휘 head가 마지막 hidden state를 어휘 전체의 logit으로 바꾼다.

A. PCD (parallel constrained decoding)

기존 LLM을 학습 없이 그대로 쓴다. 답 빈칸에서 보기 첫 토큰의 점수만 읽는 1절의 방식에, 메일을 한 번만 읽는 2절의 묶기를 더했다.14725

대표 모델: harshatheg Qwen-2.5-1B-RLCD7, stephanj parallelConstraintDecoding, openjev-sglang, Jobe.25

깊이 보기: 계열 A의 세부와 한계

동작 단계는 2절의 PCD와 같다. 구현은 질문을 필드라 부른다.

  • forward pass: 호출 하나에 2회(prefill 1회와 질문 배치 1회). 첫 토큰이 같은 보기가 있으면 단계마다 1회가 더 든다. 자체 보고14
  • 학습하는 것: 없음. 이름에 RLCD가 붙은 LFM 모델도 학습하지 않았다고 밝힌다.26
  • 저자가 밝힌 한계: 두 엔진의 결과 차이는 디코딩이 아니라 서로 다른 프롬프트에서 나왔다.14

B. 글자 logit + fine-tuning

보기에 A, B 같은 글자를 붙이고, 답 빈칸에서 그 글자의 점수만 읽는다. 모델은 이 일에 맞게 fine-tuning한다.13

대표 모델: decider, Hopper, Jebadiah-27B, Nimble, Intern-Decision.

깊이 보기: 계열 B의 실제 예와 한계

1절의 logit 읽기에 fine-tuning을 더한 계열이다.

  • forward pass: 호출 하나에 1회. decider는 질문 N개의 답 자리를 한 번에 읽는다.13 Hopper는 보기가 26개를 넘으면 토너먼트로 나눠, 보기 77개에 forward pass 4회를 쓴다. 자체 보고15
  • 학습하는 것: 모델 전체 또는 LoRA. loss는 5절이 다룬다.
  • 변형: Intern-Decision은 보기를 한 토큰 기호로 바꾸고 답 자리 직전의 logit을 읽는다.27 lev는 문자 logit과 후보 경로 head를 함께 쓴다.5 Together Tev1은 예외로 문자 하나를 실제로 생성한다.28
  • 저자가 밝힌 한계: forward pass 한 번으로는 다단계 산술을 못 한다(1절).13

C. candidate head

글자 점수표 대신, 보기마다 끝 토큰의 hidden state(모델 안에서 토큰마다 만드는 숫자 벡터)를 꺼내 전용 채점기(후보 head)로 점수를 매긴다.8

대표 모델: Decision 1.0 Eos, Sol, Nox, Lux, MoJev, NanoJev, Kev.

깊이 보기: 계열 C의 단계별 순서, 점수 식, 한계

Decision 1.0 논문의 순서다.8

  1. 상태, 질문, 후보 블록들, 결정 접미를 이어 붙인다. 후보 블록 하나는 보기 key와 설명이다.
  2. vocabulary head를 뗀 Qwen3.5 백본으로 forward pass를 한 번 한다.
  3. 후보마다 블록 마지막 토큰의 hidden state를 꺼낸다. 이 벡터가 후보를 대표한다.
  4. 접미 마지막 위치의 hidden state를 꺼낸다. 이 벡터가 질문 전체를 요약한다.
  5. candidate head가 후보 벡터와 질문 벡터의 짝마다 점수 하나를 낸다. 점수는 두 벡터의 내적 항과 작은 신경망 항의 합이다.
  6. 점수를 온도로 나누고 후보 전체에 softmax해 확률을 만든다.
  7. Choice는 확률이 가장 큰 후보를 고른다. Noul은 true 후보의 확률을 낸다. Score는 확률로 가중한 단계 번호를 낸다.

논문 3.2절의 식 3이다. h_i는 후보 i의 끝 hidden state, h_q는 접미 끝 hidden state다.8

c_i = LN_c(h_i);  q = LN_q(h_q)
z_i = (W_k c_i)^T (W_q q) / sqrt(d_h)  +  w^T GELU(A_c c_i + A_q q + b),   d_h = 256
p(i) = exp(z_i / T) / sum_k exp(z_k / T)       (padded candidates masked)
  • forward pass: 질문 하나에 1회. 질문 사이에 상태 계산을 재사용하지 않는다.8
  • 학습하는 것: candidate head와 백본. 논문은 전체 모델 적응을 Eos에만 명시한다. Sol, Nox, Lux의 학습 범위는 논문에 없다. 미확인8
  • 다른 모델: MoJev는 readout이 후보마다 logit 하나를 낸다.19 NanoJev는 백본이 후보 경로를 인코딩하고 공유 head가 확률을 낸다.29 Kev의 pointer head도 보기 끝 토큰을 점수화하므로 이 계열로 묶는다.22
  • 저자가 밝힌 한계: 출력 토큰을 없앤 것만으로 한 토큰 생성 분류기보다 빠르다고 할 수 없다(1절).8

D. 보기별 점수화

메일과 보기 하나를 짝지어 보기마다 따로 계산한다. 쓰는 모델은 cross-encoder(두 글을 함께 읽는 분류 모델)다. 보기가 K개면 계산도 K번이다.30

대표 모델: AlexWortega openjev.

깊이 보기: 계열 D의 세부와 한계

AlexWortega openjev는 NLI cross-encoder 하나를 쓴다. NLI는 전제가 가설을 지지하는지 판정하는 작업이다.30

  • forward pass: 보기마다 1회, 보기 K개면 K회. 보기 순서는 답을 바꾸지 않는다. 자체 보고30
  • 학습하는 것: Qwen3.5 시퀀스 분류 모델 전체(라벨 3개).
  • 다른 모델: pngwn scorer는 보기별 점수를 forward pass 한 번에 낸다.31
  • 저자가 밝힌 한계: 프롬프트 인젝션에 약하다. 상태에 적대적 한 줄을 넣으면 JevBench 150문항 정확도가 0.833에서 0.467로 떨어진다. 자체 보고30

E. RL 인코더

보기마다 [MASK] 표시를 붙이고 그 자리의 점수를 읽는다. 모델은 앞뒤를 모두 보는 인코더다32.

학습은 정답을 직접 주는 대신, 모델이 낸 확률에 점수만 매겨 주는 RL로 한다.

  1. 시도. 보기 점수에 무작위 잡음을 더해 후보 확률 몇 개를 만든다. 예: yes 90%, 60%, 75%.
  2. 채점. 실제 답과 비교해 후보마다 보상을 준다. 보상은 proper scoring rule로 계산한다. 이 규칙은 믿는 확률을 그대로 말할 때 점수가 가장 좋아서, 과장하면 손해다.
  3. 이동. 평균보다 보상이 큰 후보 쪽으로 가중치를 조금 옮긴다.

그래서 이 학습은 맞히는 것과 함께 정직한 확률(4절 보정)을 노린다. 단계별 그림은 5절 그림 5-1에 있다. Laya의 공개 fine-tuning 코드는 이 RL 항에 soft cross-entropy(supervised learning loss)도 더한다45.

대표 모델: Laya.

깊이 보기: 계열 E의 세부와 한계

C는 후보 블록의 끝 토큰을 읽고, E는 보기마다 일부러 넣은 표시 토큰을 읽는다. Laya의 인코더는 ModernBERT-large이고 decision head가 붙는다.32

  • forward pass: 호출 하나에 배치 forward pass 1회다. 질문마다 입력이 하나씩 배치에 들어가므로, 시간은 질문 수에 따라 는다. T4에서 질문 1개는 39.5 ms, 10개는 158.6 ms다. 자체 보고32
  • 학습하는 것: 인코더 전체와 처음부터 학습한 decision head.32
  • 다른 사례: decider v10은 B의 문자 logit 위에 RL 단계를 더한 사례다.33
  • 저자가 밝힌 한계: 보기들이 고정 토큰 예산을 나눠 쓴다. 보기가 77개면 라벨당 3-4 토큰만 남는다. 그래서 Banking77 정확도가 0.425(77 라벨)이고, Laya가 인용한 Jev 수치는 0.870(72 라벨)이다. 자체 보고32

F. text diffusion

text diffusion은 글을 왼쪽부터 한 토큰씩 쓰지 않는다. 정해진 길이의 토큰 판 전체를 놓고 여러 번 고쳐 쓴다. 흐린 사진을 여러 번에 걸쳐 선명하게 만드는 것과 비슷하다34.

  1. 답 JSON의 틀(괄호, 키)을 판에 고정한다.
  2. 빈칸은 무작위 토큰으로 채운다.
  3. 모델이 판 전체를 보고 모든 칸을 동시에 다시 쓴다. 이것이 한 단계(denoising)이고, N번 되풀이한다.
  4. 빈칸마다 허용 토큰 중 점수가 가장 큰 것을 고른다20.

학습하지 않은 DiffusionGemma를 그대로 쓴다25.

4. 보정

모델이 "80% 확신"이라고 한 답이 실제로 80% 맞으면, 그 모델은 보정되어 있다.

보정은 답 하나가 아니라 답 묶음의 성질이다. "80% 확신" 답 하나가 맞는지는 보장하지 않는다24.

보정을 숫자 하나로 잰 것이 ECE(expected calibration error)다. 확률 구간마다 "말한 확률"과 "실제 정답률"의 차이를 구하고, 구간의 답 수로 가중 평균한다. 0이면 완벽하다. 그림 4-1의 모델 B는 답이 모두 80% 구간에 있으므로 ECE가 0.8 − 0.6 = 0.2이고, 모델 A는 0이다. 계산식과 예는 아래 상자에 있다.

깊이 보기: 보정을 재는 수, ECE와 Brier 점수

ECE(expected calibration error)는 보정 오차를 한 수로 줄인 값이다. 0이면 완벽하다. 계산은 세 단계다.

  1. 답을 확률 구간으로 나눈다.
  2. 구간마다 평균 확률과 실제 정답률의 차이를 구한다.
  3. 그 차이를 구간의 답 수로 가중 평균한다.

예를 들어 평균 확률 0.9인 구간에 답 50개가 있고 정답률이 0.7이라고 하자. 평균 확률 0.6인 다른 구간에도 답 50개가 있고 정답률이 0.6이다. ECE는 0.5×0.2 + 0.5×0 = 0.1이다.

Brier 점수는 답마다 확률과 실제 결과(맞으면 1, 틀리면 0)의 차이를 제곱해 평균한 값이다. 낮을수록 좋다. yes에 0.8을 주고 yes가 맞으면 (1−0.8)² = 0.04이고, no가 맞으면 0.8² = 0.64다. ECE와 달리 Brier 점수는 정확도와 보정을 함께 반영한다.

ECE   = Σ_b (n_b / N) × | acc_b − conf_b |
        b: 확률 구간 (그림 4-4는 폭 0.1인 구간 10개)
        n_b: 구간 b의 답 수, N: 전체 답 수
        acc_b: 구간 b에서 실제로 맞은 비율 (그림에서는 실제 yes 비율)
        conf_b: 구간 b의 평균 확률

Brier = (1/N) × Σ_i (p_i − y_i)²
        p_i: 답 i에 준 yes 확률, y_i: 실제 결과 (yes = 1, no = 0)
        선택지가 여럿이면 선택지마다 (p − y)²를 더한다.

온도   p = softmax(z / T)
        yes/no 하나의 logit z이면 p(yes) = 1 / (1 + exp(−z / T))

왜 결정 모델에서 더 중요한가

결정 모델의 확률은 사람보다 프로그램이 먼저 보고 행동한다. 예를 들어 "확신 90% 이상이면 자동 환불"처럼 쓴다.

근거 보기: TypeSafe 문서와 자동 처리 비율

TypeSafe 문서는 confidence 임계값을 고객이 자기 데이터로 시험해 정하라고 안내한다35업체 발표. 같은 문서의 예시 코드는 confidence 0.5 미만을 정말 불확실한 답으로 다룬다35. TypeSafe는 학습 목표를 "확률이 높을수록 답이 맞을 가능성도 커야 한다"로 적는다24업체 발표. 홈페이지는 RLHF가 과신을 낳아 사람의 개입이 필요해진다고 주장한다36업체 발표.

흔한 구성은 임계값 위의 답을 자동으로 처리하고 아래의 답을 사람에게 보내는 것이다. 채팅 모델은 사람이 답을 읽고 거르므로 같은 과신이 행동으로 바로 이어지지 않는다.

Kev 저자는 오류를 5% 안에 묶을 때 자동 처리할 수 있는 답의 비율(5% 오류 예산의 자동 처리 비율)을 쟀다. 0.70이면 답 100개 중 70개를 자동 처리해도 오류가 5% 이내라는 뜻이다. Kev 4B/9B/27B는 0.52–0.69, Jev는 0.70이다23자체 보고. TypeSafe가 공개한 보정 정량 수치는 확인되지 않았다미확인.

온도: 확신의 크기를 조절하는 다이얼

온도 T는 확률을 만들기 전에 점수(logit)를 나누는 수다. 답의 순위는 그대로 두고 확신의 크기만 바꾼다.

학습이 끝난 뒤 따로 떼어 둔 데이터로 T 하나를 골라 고정하는 보정 방법을 temperature scaling이라 한다. 여러 결정 모델이 이 방법을 쓴다27자체 보고. 하는 이유는 셋이다.

  • 모델은 흔히 과신한다. Hopper는 Banking77에서 평균 확신 0.78, 정확도 0.67이었다15자체 보고. T를 1보다 크게 잡으면 확신이 줄어 실제 정답률에 맞춰진다.
  • 싸고 안전하다. 다시 학습하지 않고 숫자 하나만 정한다. 모든 logit을 같은 수로 나누므로 1등 답과 정확도는 그대로다.
  • 결정 모델에 필요하다. "확신 90% 이상이면 자동 처리" 같은 규칙은 확률값 자체를 믿고 움직인다(그림 4-2).

주의할 점이 둘 있다. 이 온도는 글의 다양성을 정하는 샘플링 온도와 이름만 같다27. 또 확률이 임계값을 넘는지로 채점하면 온도가 결과를 바꾼다. 7절의 Noul 기권 규칙(yes 확률 0.20 초과 0.80 미만이면 기권)이 그런 채점이다.

아래 그림에서 온도를 직접 바꿔 본다. 데이터는 지어낸 yes/no 결정 400개다. 막대 끝이 점선(완벽한 보정)에 닿을수록 보정이 잘 된 것이다.

온도를 바꿔도 1등 답과 정확도(77.5%)는 그대로이고, ECE와 Brier 점수가 달라진다.

온도를 바꾸면 막대 높이가 들쭉날쭉 바뀌고, 이웃 구간끼리 높이 순서가 뒤집히기도 한다. 예: T=1에서 0.6–0.7 구간은 0.76인데 0.7–0.8 구간은 0.54다. 답의 순위가 바뀐 것은 아니다. 이유는 둘이다.

  • 답이 구간을 옮겨 다닌다. 구간은 확률 범위로 고정되어 있다. 온도가 바뀌면 답의 확률이 바뀌어 다른 구간으로 들어가고, 구간마다 담긴 답이 달라진다.
  • 가운데 구간은 답이 적다. 20개 안팎이라 실제 비율이 우연에 크게 흔들린다. 답 몇 개만 달라도 막대가 크게 움직인다.

그래서 막대 하나보다 전체 흐름과 ECE를 본다. 데이터가 많을수록 막대는 매끄러워진다.

TypeSafe는 Jev의 학습 방법을 RLCD(Reinforcement Learning for Calibrated Decisions)라고 부른다1. 공개된 정의는 한 줄이다. 글 대신 결정과 보정된 확률을 내도록 학습한다24.

이름에 RL이 들어 있지만, 보상 함수, 정책 구조, 데이터 구성은 공개되지 않았다 미확인.

같은 이름, 다른 내용

근거 보기: 세 가지 쓰임의 세부
  1. 문서화된 RL. Laya는 RLCD라는 이름으로 RL 항을 구현했다. 행동은 모델이 보고하는 분포이고, 보상은 proper scoring rule이다. logit에 무작위 잡음을 더해 여러 분포를 시도하고, 평균 보상보다 나은 시도 쪽으로 가중치를 옮긴다.32 자체 보고 공개된 fine-tuning 코드는 이 항에 소프트 cross-entropy를 더해 함께 쓴다. 소프트 cross-entropy는 타깃 분포를 직접 맞히는 supervised learning loss다. 저자의 코드 주석은 RL 항이 typed-decisions 분할에서 이득이 없었다고 적는다.45 자체 보고 Laya에서 파생한 Lavoir는 이 항을 껐다.46 자체 보고 decider v10의 RL 단계(위 상자)는 RLCD라는 이름을 쓰지 않는다.
  2. supervised learning에 붙인 이름. heman10x의 ModernBERT-151M은 이름에 RLCD를 쓰지만, 카드가 적은 학습은 cross-entropy와 Brier loss, 사후 온도 맞춤이다.40 자체 보고 NanoJev는 RLCD 학습을 미완료 로드맵 항목으로 두고 supervised learning만 한다.29 자체 보고
  3. 학습 없이 빌린 이름. harshatheg/Qwen-2.5-1B-RLCD는 가중치 없이 수정 없는 원본 모델과 디코딩 코드만 담는다.14 monotykamary/LFM2.5-2.6B-RLCD는 TypeSafe의 RLCD를 재현한 것이 아니라고 직접 밝힌다.26 자체 보고

표 주석 보기: 계열, 값의 출처, 각주
  • 계열. B는 글자 logit 읽기, C는 candidate head(pointer head, joint schema head 포함), E는 RL 인코더다(3절). 미확인은 해당 판의 카드가 읽는 방식을 적지 않은 경우다. Bespoke Nimble은 v2 카드가 허용 후보 logit을 읽는다고 적었지만(3절 계열 B), v3 카드는 적지 않았다.
  • 값의 출처. DI 점수와 공개 점수, ECE, 크기는 Decision Index 0.3 데이터다41. JevBench 열은 v1.6.1 결과 JSON의 Capability와 공개 보드 공식 순위다63. 라이선스는 Hub 메타데이터, 하드웨어는 카드가 적은 값이다 자체 보고.

  • ² Hopper 12B. Hub 저장소의 기본 브랜치는 4B이고 12B는 별도 브랜치다. Hub 라이선스 표기는 other이고, 카드는 12B를 Apache-2.0으로 적는다. 글자 logit 읽기는 4B에만 적혀 있어 12B의 계열은 미확인으로 두었다.

근거 보기: 보정 주장 문장과 ECE 수치

트래커의 보정 문장과 Decision Index의 ECE 수치는 서로 다른 것을 재므로 나란히 놓아 읽는다.

  • 트래커: 공개 가중치 모델은 후보 logit에 softmax를 쓰고, 연구들은 모델의 확률이 오류를 믿을 만하게 가려내지 못한다고 본다. 이 문장은 ECE 수치를 들지 않는다25.
  • Decision Index 0.3: 전체 ECE는 Jev 0.074다. 자체 가중치가 있는 모델 중 가장 낮은 셋은 Jebadiah 27B 0.014, Kev 27B 0.0218, Decider 35B-A3B 0.0226이다41. 표본 수는 모델마다 다르다(Jev 72,594개, Jebadiah 35,093개). ECE의 뜻은 4절에 있다.

이 문서는 어느 쪽이 Jev의 보정 주장에 맞는지 판정하지 않는다. 평가 쪽 수치는 7절에 있다.

결정 모델의 순위를 매기는 리더보드는 둘이다. Decision Index는 얼마나 맞히는지만 보고, JevBench는 확률의 정직함(보정)과 비용, 속도까지 본다.

Decision Index는 공개 벤치마크 37개와 비공개 시험을 결정 형식으로 바꿔 정확도를 재는 커뮤니티 리더보드다41. JevBench는 Benchmark Heaven이 직접 만든 결정 1,500건으로 보정까지 재는 벤치마크다62. 두 곳 모두 TypeSafe와 관계가 없다고 밝힌다5659.

입력이 모델의 층을 한 번 통과해 출력 숫자가 되는 계산이다. 1절

상태를 한 번 계산한 뒤 질문별 시퀀스를 배치로 묶어 허용 토큰의 logit을 병렬로 읽는 방식이다. 2절
Score
순서 있는 수준 척도에서 점수를 매기는 질문 타입이다. 수준은 2~10개다. 2절
text diffusion (텍스트 디퓨전)
고정 길이의 토큰 판 전체를 여러 단계에 걸쳐 동시에 고쳐 쓰는 방식이다. 토큰을 앞에서부터 하나씩 쓰지 않는다. 3절
fine-tuning (미세조정)
사전학습된 모델을 새 목적의 데이터로 조금 더 학습시키는 일이다. 3절
LoRA
base model을 고정하고 작은 저랭크 행렬만 학습하는 fine-tuning 방식이다. 3절
head (헤드)
모델 몸통 위에 얹어 내부 표현을 점수나 확률로 바꾸는 작은 출력 층이다. 3절
prefill (프리필)
입력 전체를 한 번 통과시켜 KV cache를 만드는 첫 forward pass 단계다. 3절
hidden state (은닉 상태)
모델 층이 토큰마다 만드는 내부 숫자 벡터다. head가 이를 점수로 바꾼다. 3절
cross-encoder (교차 인코더)
상태와 보기 하나를 이어 붙여 함께 읽고 점수 하나를 내는 모델이다. 3절
supervised learning (지도학습)
입력마다 정답 라벨을 주고 그 라벨에 대한 loss를 줄이는 학습이다. 3절
cross-entropy (교차 엔트로피)
정답 라벨에 낮은 확률을 줄수록 커지는 loss다. 3절
온도 (temperature)
logit을 나누는 양수다. 클수록 확률 분포가 평평해진다. 4절
보정 (calibration)
확률 0.8로 낸 답의 약 80%가 맞는 성질이다. 집단 수준의 속성이다. 4절
proper scoring rule (적절한 점수 규칙)
참 확률을 정직하게 보고할 때 기대 점수가 가장 좋아지는 점수 함수다. 4절
RLHF (reinforcement learning with human feedback)
사람이 고른 답을 보상으로 채팅 모델을 다듬는 학습이다. 4절
ECE (expected calibration error)
구간별 평균 최고 확률과 정확도의 차이를 가중 평균한 값이다. 낮을수록 좋다. 4절
Brier 점수 (Brier score)
예측 확률과 실제 결과(0 또는 1)의 차이를 제곱해 평균한 값이다. 낮을수록 좋다. 4절
RPS (ranked probability score)
순서 있는 단계에서 누적 확률의 오차를 재는 점수다. 4절
RLCD
TypeSafe가 Jev에 쓴다고 밝힌 학습 방법(Reinforcement Learning for Calibrated Decisions)이다. 알고리즘 세부는 미확인이다. 5절
loss (손실)
학습 중 줄이려는 숫자다. 예측이 틀릴수록 커진다. 5절
RL (reinforcement learning, 강화학습)
모델의 행동 결과에 점수(보상)를 주고 그 점수를 높이도록 학습하는 방법이다. 5절
공개 가중치 (open weights)
가중치 파일이 공개되어 내려받아 쓸 수 있는 모델이다. 6절
JevBench
benchmarkheaven의 단일 벤치마크다. 항목은 상태, 질문, 정답 라벨로 이루어진다. 7절
Jev급 (Jev-class)
비용과 중앙값 지연이 둘 다 Jev의 2배 이하인 시스템이다. JevBench는 이 범위 안의 시스템만 공식 비교한다. 7절
Capability
JevBench의 총점이다. 정확도(Intelligence)와 보정(Calibration)의 평균이다. 7절
Decision Index
Hugging Face Space의 커뮤니티 리더보드다. 0.3판은 공개 벤치마크 37개와 비공개 시험을 합쳐 Full score를 낸다. 7절
TVD (total variation distance)
두 확률 분포가 얼마나 다른지 재는 거리다. 7절
